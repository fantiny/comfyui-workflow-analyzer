# ComfyUI 工作流业务文档

当用户需要理解、教学或记录一个或多个 ComfyUI 工作流 JSON 时使用此 skill。

## 核心原则

必须从用户要完成的业务任务反向解释工作流，而不是从节点列表正向罗列。每个主要部分都要回答：

> 用户想得到什么结果？这一组节点对这个结果具体贡献了什么？

避免使用“把数据传给下一个节点”“形成连续处理流程”或仅仅重复节点名称和类型等无效描述。

## 必须完成的分析

1. 读取 workflow JSON，包括节点类型、参数值、输入输出端口、连线、模型名称、提示词、遮罩、尺寸和输出节点。
2. 根据文件名、提示词、输入素材、模型类型和节点图识别具体业务目标，例如换装、保持人物身份、移除物体、参考帧生成视频、放大修复。
3. 按业务拆分最小有意义的功能子流程：准备原图和参考素材、定义编辑边界或结构控制、转换模型条件、注入风格或身份、生成或编辑、解码修复和导出。
4. 对每个子流程找出最小有效节点组合，并说明删除或错误配置该组合后，业务结果会发生什么变化。
5. 当自定义节点仅凭端口和参数无法确定作用时，查阅官方模型或自定义节点文档、源码。无法确认的内容必须标记为“需实测确认”，禁止臆测。

## 文档必须包含

1. **业务目标**：用一段易懂的话说明最终要完成的任务。
2. **输入与输出**：说明原图或原视频、参考素材、遮罩、提示词、模型和最终结果。
3. **总流程图**：只显示业务功能组，不显示所有节点。
4. **子功能说明**：每个子功能包含节点组合、业务作用、节点与业务动作的对应关系、组合原因和关键参数影响。
5. **子功能流程图**：每个子功能一张 Mermaid 图，只显示该功能组内的节点和连线。
6. **调参顺序**：按照业务影响排序，通常先调遮罩或编辑边界，再调参考素材、提示词或条件、强度或引导、随机种子，最后调性能参数。
7. **失败现象与排查**：把可见结果直接对应到可能的工作流原因。
8. **依赖与验证边界**：列出模型文件、自定义节点，并区分推断内容和实际运行验证内容。

## 写作标准

- 优先写“参考图 + 遮罩 + ACEPlusFFTProcessor，实现指定区域换装”，不要写“LoadImage 连接到 ACEPlusFFTProcessor”。
- 单个节点的具体作用只在节点表中详细说明一次；子功能部分重点解释节点组合和业务效果。
- 总流程图必须保持简洁，不能把全部节点塞进一张图。
- 参数和故障排查使用表格。
- 明确区分证据、推断和运行验证；没有验证时不得声称效果、速度或兼容性已经确认。
